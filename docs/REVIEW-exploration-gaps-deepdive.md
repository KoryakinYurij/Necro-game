## 0. Сводка: что реально нужно от ядра (минимальная поверхность адаптера)

Главный вывод углублённого разбора: **почти весь пивот делается через УЖЕ экспортированный
`__necro.P6` (конфиг-функции) и мутабельные ссылки на объекты врагов.** Настоящих новых
патчей ядра требуется минимум. Сводная таблица:

| Возможность | Как достигается | Нужен ли новый патч ядра? |
|---|---|---|
| Отключить ambient-спавн орд | `P6.threatRate = () => 0` | **Нет** (P6 экспортирован) |
| Отключить timed boss/wave/elite | прижать `a.nextBoss/nextWave/nextElite/phaseT = 1e9`, `a.threat=0` каждый тик | **Нет** (мутация `G`) |
| Spatial difficulty вместо времени | `P6.hpTime/dmgTime = f(dangerTier)` | **Нет** (P6 экспортирован) |
| Явный спавн группы в точке мира | экспортировать `H(type,x,y)` как `N.spawn` | **Да, 1 точечный патч** |
| Per-frame оркестрация (proximity/leash/маркеры) | hook в конце `sr` (`window.__nxUpdate?.(dt)`) или экспортировать `ur` | **Да, 1 точечный патч** |
| Render мировых маркеров под сущностями | оверрайд `gfx.floor` (уже экспортирован) | **Нет** (gfx.floor есть) |
| Выдача POI-наград | `a.relics.push(id)/a.pacts.push(id); N.recalc()` | **Нет** (паттерн уже в nx_progression) |
| Управление составом/аффиксами по danger | прямой выбор типа в `N.spawn` + `a.biomeIdx` (аффикс-пул) | **Нет** |

**Итого: для тонкого среза нужно добавить всего ~2 точечных экспорта ядра** (`spawn` и
`__nxUpdate`-хук). Всё остальное — через существующий фасад. Это сильное подтверждение
реалистичности ADR-0002 и резко сужает поверхность хрупких string-патчей (G2).

## G1. Time-coupling сложности — механизм и решение (P0)

### Что фактически делает код
Три независимых канала, где время (`a.time`, сек; `r=a.time/60`, мин) управляет сложностью:

**(1) Непрерывный ambient-спавнер** (внутри `sr`, offset ~145257):
```js
for (a.threat = (a.threat||0) + t*j.threatRate(r);   // t=dt, r=a.time/60
     a.threat>0 && a.enemies.length<i; ) {           // i = maxEnemies (220)
  let e=Ht();                 // выбор типа врага (по threat/биому)
  if(!e) break;
  let tc=ye[e]||1;            // ye = "стоимость" типа: zom:1 … elite:16, boss:45
  if(a.threat<tc) break;
  a.threat-=tc, Rt(e);        // Rt = спавн КОЛЬЦОМ ВОКРУГ ИГРОКА
}
```
`threatRate(e)=Math.min(32,1.2+e*2.6+e**1.45*.6)` — **растёт от времени**; в рантайме
обёрнута: `t*=Dr()` (фаза wave/lull/event) и пактами (swarm ×1.35, famine ×0.92).

**(2) HP врагов** (внутри `H`, offset ~91116): `s.maxhp=s.hp=Math.round(i.hp*St()*variance)`,
где `St()=j.hpTime(a.time/60)*(1+min(cap, xt()*powerScale.hp))`. `xt()` — сила игрока
(уровень+оружия+эволюции) → это **мягкая** поправка (совпадает с ADR-0003).

**(3) Урон врагов** (в момент удара, `z()`): `z()=j.dmgTime(a.time/60)*(1+…xt()*…)`.
Внимание: `s.dmg=i.dmg` в `H()` — **базовый, не масштабируется при спавне**; `dmgTime`
применяется в рантайме при каждой атаке, т.е. урон растёт от времени **в течение всего боя**.

### Конкретное решение (через P6, без патчей)
```js
// в nx_exploration.js, при входе в exploration mode:
const P6 = N.P6;
P6.threatRate = () => 0;                 // (1) убивает ambient-спавн полностью
P6.hpTime     = (_t) => hpCurve(curDanger());   // (2) HP от danger-tier, НЕ от времени
P6.dmgTime    = (_t) => dmgCurve(curDanger());  // (3) урон от danger-tier
// + каждый тик прижимать таймеры (страховка от timed-событий):
G.nextBoss = G.nextWave = G.nextElite = G.phaseT = 1e9; G.threat = 0; G.phase = 'wave';
```
- `curDanger()` — функция exploration-слоя: tier текущей зоны/encounter (по расстоянию от
  спавна / по authored- composition). Выставляется **до** вызова `N.spawn(...)` для HP
  (т.к. `St()` зовётся синхронно внутри `H`) и держится на время боя для `dmgTime`.
- `_t` (аргумент-время) намеренно игнорируется — это и есть «разрыв» time-coupling.

### Тонкость, которую обязательно учесть
`dmgTime` применяется **в момент удара**, а не при спавне. Значит «danger» во время боя
должен быть определён (какой encounter/зона сейчас дерётся). Для v0.1 достаточно
**глобального `curDanger` = tier активного encounter'а**; при нескольких активных — max/ближайший.
HP же фиксируется при спавне (проще). Это асимметрия, которую надо явно закодить и протестить.

### Тест-кейсы (пишутся ДО реализации спавна — дексируют риск)
1. **director-off:** старт exploration → `step(1/60)` × (3 сим-минуты) → `G.enemies.length===0`,
   ни одного `nextBoss/Wave/Elite`-события, `phase` не менялся.
2. **danger-не-от-времени (HP):** заспавнить группу tier=1, прогнать 5 сим-минут без боя,
   заспавнить tier=1 снова → `maxhp` одинаков (время не повлияло).
3. **danger-меняет-HP (пространство):** tier=1 vs tier=3 в один момент → `maxhp(t3) > maxhp(t1)`
   качественно (не просто +HP: проверить и состав/аффикс, см. #7).
4. **waiting-no-escalation:** тот же enemy, `step` на +10 сим-минут → его `dmg` (через z) не вырос.
5. **arena-контроль:** в Arena Mode `threatRate` восстановлен → ambient-спавн идёт (регрессия).

### Остаточный риск
Если забыть хоть один канал (например, оставить `dmgTime` от времени), игра молча вернёт
time-scaling → нарушение ADR-0003. Митигейт: тесты 2 и 4 выше как обязательные инварианты #8.

## G3. Leash / disengage — новая логика (P1)

### Что фактически делает код
Enemy-update в `sr` (offset ~93041):
```js
for (let i of a.enemies){
  if(i.dead) continue;
  let o=i.spd*(i.slowT>0?i.slowF:1),
      s=Math.atan2(t.y-i.y, t.x-i.x),   // t = ИГРОК: угол строго на игрока
      c=Math.cos(s)*o, l=Math.sin(s)*o;
  // … i.x += c*dt; i.y += l*dt  (движение к игроку)
  // аффиксы: fire/vortex/storm — свои спец-атаки
}
```
**Вывод:** враги идут прямо на игрока **каждый кадр, глобально, без якоря и без отставания.**
Нет `despawn`, нет границ (подтверждено grep'ом). Для exploration это = «бесконечный поезд
через всю карту», что прямо запрещено спекой (#1, #4).

### Конкретное решение (внешний leash, без патча enemy-AI)
`H()` **возвращает** объект врага и он лежит в `a.enemies` по ссылке → exploration-слой
владеет ссылками на всех заспавненных врагов encounter'а. В per-frame хуке (см. G-tick ниже):
```js
for (const enc of activeEncounters){
  const dPlayer = dist(enc.anchor, player);
  if (dPlayer > enc.leashRadius){          // игрок увёл бой далеко от якоря
    for (const e of enc.enemies){
      if (e.dead) continue;
      const dAnchor = dist(enc.anchor, e);
      if (dAnchor > enc.enemyLeash){        // враг оторвался от якоря
        // вариант A (мягкий): тянем врага обратно к якорю
        e.x += (enc.anchor.x-e.x)*0.08; e.y += (enc.anchor.y-e.y)*0.08;
        // вариант B (жёсткий): e.dead=true; enc.aliveCount--
      }
    }
    // disengage: если игрок вне радиуса N секунд → enc.state='dormant' (не cleared!)
  }
}
```
- **Вариант A** сохраняет «живость» (враги возвращаются к месту) — лучше для feel.
- **Вариант B** проще и гарантированно не даёт поездов. Для v0.1 достаточно B + re-activate.
- Ключевое: disengaged encounter возвращается в `dormant` (НЕ `cleared`) → его можно
  re-trigger, но награда не выдаётся повторно (idempotency из #4/#5/#6 сохраняется).

### Тест-кейсы
1. **leash-holds:** активировать encounter, увести игрока на 3× радиус, `step` 2 сек →
   все враги в пределах `enemyLeash` от якоря (или dead), ни один не ушёл за игроком.
2. **disengage-to-dormant:** увести игрока далеко и подождать → `enc.state==='dormant'`,
   живых врагов 0, encounter **не** `cleared`.
3. **re-engage:** вернуться → encounter снова активируется; **cleared-награда не выдаётся дважды**.
4. **no-train:** заспавнить 2 encounter'а, активировать оба, бежать по кругу → суммарно
   живых врагов ≤ (`leash`-ограничение), нет растущего хвоста.

### Остаточный риск
Прямая мутация `e.x/e.y` из внешнего слоя конфликтует с ядром, которое в тот же кадр двигает
врага к игроку. Порядок важен: хук должен выполняться **после** enemy-update ядра (см. G-tick:
хук в **конце** `sr`), иначе ядро перезапишет позицию. Это надо зафиксировать.

## G-tick. Per-frame simulation hook — необходимый новый шов (P0, кросс-гаттеринг)

### Проблема
Exploration-оркестрации нужен **ежекадровый** тик в фазе симуляции (проверять proximity →
активировать encounter'ы, применять leash, обновлять danger, класть маркеры). Что есть сейчас:
- `step(dt)` → зовёт `sr(dt)` — **только для headless-тестов**; живой геймплей идёт через
  собственный rAF-цикл ядра `lr(e)`, который зовёт `sr(n), ir(), rr(n)` напрямую.
- `var ur=e=>{sr=e}` — сеттер `sr` **есть в ядре, но НЕ экспортирован** в `__necro`.
- gfx-хуки (`gfx.floor/enemy/hero/...`) — это **фаза рендера** `ir`, не симуляции.
  Спека #2 прямо запрещает «независимый неконтролируемый animation loop» и требует
  «правильный игровой слой».

### Решение (1 точечный патч ядра)
Добавить в конец `sr` (или экспортировать `ur`) хук:
```js
// build.py CORE patch: в конец функции sr, после enemy-update и до return:
//   … , window.__nxUpdate && window.__nxUpdate(dt)
```
Тогда exploration-слой:
```js
window.__nxUpdate = (dt) => { updateWorldState(dt); activateByProximity(); applyLeash(); syncDanger(); };
```
- Хук в **конце** `sr` ⇒ выполняется после движения врагов ядра ⇒ leash-мутации не затираются (см. G3).
- Это **единственный** обязательный новый симуляционный шов; альтернатива — экспортировать `ur`
  и обернуть `sr` (чище, т.к. не трогает тело `sr`, но требует аккуратной обёртки).

### Тест-кейс
- **hook-fires-and-controls:** повесить `__nxUpdate`, `step(dt)` → хук вызван; encounter в
  радиусе proximity активировался; вне радиуса — нет. (Покрывается инвариантами #4.)

## G4. POI-награды и level-up UX — механизм выдачи (P1)

### Что фактически делает код (текущий reward-поток)
XP-драфт (offset ~76012): `a.xp>=a.need → a.level++, a.queue++`; затем
`a.queue>0 && i==='play' → mt(!1)`; `mt()` ставит `i='levelup'`, строит модалку карт
`ht()` из пула `pt()`, выбор применяется, `a.queue>0?mt(!1):l('play')`. Т.е. **билд-выбор
сегодня = паузо-модалка, привязанная к XP/киллам.** Спека (US 10–11, §26.8) хочет, чтобы
**сильные** решения приходили из POI, а XP был «поддерживающим».

### Seam, который УЖЕ доказан в репозитории
`nx_progression.js` выдаёт награды **без драфта**, напрямую в run-state:
```js
N.G.relics.push(relicId); N.recalc();     // строки 178/235/238
N.G.pacts.push(pactId);   N.recalc();     // строка 212
// + свой UI (панели «Пути некроманта», испытания, печати) — тоже через __necro
```
`N.recalc()` пересчитывает статы после изменения `relics/pacts`. Это и есть готовый механизм
выдачи «место-ориентированной» награды.

### Конкретное решение для POI
- **POI-награда (Ruins/Altar)** = отдельный reward-поток exploration-слоя:
  1. encounter/POI переходит в `cleared`;
  2. exploration-слой показывает **свой** reward-выбор (2–3 опции), как nx_progression показывает свои панели;
  3. по выбору — `N.G.relics.push(id)` / `N.G.pacts.push(id)` (+ возможно weapon) → `N.recalc()` → `N.save()`;
  4. награда **one-time** (POI помечается claimed в world-state; повторный вход не выдаёт).
- **XP-драфт остаётся**, но делает «поддерживающий» рост: для v0.1 достаточно, чтобы POI-награда
  была качественно крупнее (реликт/пакт/оружие) против +1 уровень статов. Опционально — soften
  XP-кривую (`be(level)`), но это уже баланс, не блокер.

### Почему это неbloated
Не надо переписывать драфт или level-up. POI-награды живут **снаружи** ядра тем же паттерном,
что и вся мета-прогрессия. Единственное новое — reward-UI exploration-слоя (аналог панелей
nx_progression) + логика one-time-claim в world-state.

### Тест-кейсы
1. **poi-reward-grants:** очистить Ruins → выбрать награду → `N.G.relics` содержит id, статы
   изменились после `recalc`.
2. **idempotency:** выйти/зайти в зону Ruins повторно → награда **не** выдаётся второй раз,
   POI в состоянии `cleared/claimed`.
3. **altar-stronger:** награда Altar > награды Ruins/обычного encounter по измеримому признаку
   (редкость/число эффектов/тир реликта) — покрывает #6.
4. **xp-supporting:** фарм обычных мобов даёт XP-драфт, но суммарная «сила» ниже, чем у POI-награды.

### Остаточный риск / открытая развилка (решить до #5)
- **Weapon-награды**: выдача реликтов/пактов подтверждена (`relics.push/pacts.push`), а вот
  выдача/апгрейд **оружия** вне драфта — надо проверить seam (`a.weapons[...]`+recalc или
  нужен новый экспорт). Если оружия нет в P6/API — либо ограничить POI-награды реликтами/пактами
  для v0.1, либо добавить точечный экспорт. **Это единственная недопроверенная деталь G4.**

## G5. Рендер мировых маркеров — слой и механизм (P2)

### Что фактически делает код
Рендер-фаза `ir` (зовётся в `lr` после `sr`). Пол рисуется `Yn()` **первым**
(`fillRect(0,0,g,_); Yn(); …` offset ~138546), затем сущности. `Yn` = `gfx.floor`-хук,
**уже переопределяем** через API (`gfx:{floor:e=>{Yn=e}, enemy, hero, minion, golem, shadow}`).
Есть fog-of-war `Xn()` (radial-gradient destination-out).

### Конкретное решение
- **Наземные маркеры** (POI/encounter-иконки, комппас-стрелки у земли) → рисовать в
  оверрайде `gfx.floor`: сначала оригинальный пол, затем маркеры в мировых координатах
  через `w2s(x,y)` (экспортирован). Так маркеры окажутся **под** сущностями (правильный слой)
  и **внутри** контролируемого rAF ядра (нет отдельного loop — требование #2).
- **HUD/компас** (экранные стрелки к discovered-целям) → DOM-оверлей, как nx_ext уже делает
  HUD ритуалов (создаёт свои `<div>`). Не трогает canvas-порядок.
- Учитывать fog-of-war: маркеры далеко за пределами видимости не показывать (или показывать
  только discovered) — согласуется с «navigation intentionally minimal» (#1).

### Тест-кейс
- **marker-render-seam:** в exploration при наличии discovered POI — `gfx.floor`-оверрайд
  вызван и нарисовал маркер (проверяется через headless-рендер/спай на gfx.floor, аналогично
  smoke-проверке «gfx-слой активен»). Плюс: оригинальный пол продолжает рисоваться.

### Остаточный риск
Порядок отрисовки внутри `ir` минифицирован; надо убедиться, что маркеры не перекрывают
важные combat-элементы. Митигейт: рисовать полупрозрачно/у земли + limited marker count (#1).

## G2. Patch-drift и контракт адаптера — как не утонуть (P1)

### Факт
Сейчас ~65 string-патчей ядра в `build.py` (57 одиночных + 8 пакетных), каждый с
`assert count==N` (сборка падает при дрейфе). §7.3 уже фиксирует дрейф: `tools/balance-math.js`
содержит устаревшие формулы и анализирует «не тот рантайм». Углублённый разбор (раздел 0)
показал: **для exploration нужно добавить всего ~2 патча** (`spawn`, `__nxUpdate`), остальное —
через P6/ссылки/существующие gfx-хуки. Это хорошо: поверхность почти не растёт.

### Конкретные меры
1. **Единый модуль-адаптер** `nx_exploration.js` = единственная точка контакта с ядром.
   Внутри — явный «контракт экспортов» (список того, что слой ждёт от `__necro`), с проверкой
   при старте (`if(!N.spawn||!N.P6) → nxErr`), чтобы дрейф ядра падал **явно и рано**.
2. **Минимизировать новые патчи:** `spawn` и `__nxUpdate` — исчерпывающий список для v0.1.
   Не добавлять патч на каждый чих (danger/leash/rewards делаются снаружи).
3. **Вынос декларативных данных** (§8 ревью): начать с `enemies.js` (типы/базовые статы/`ye`-cost)
   и `danger.js` (кривые `hpCurve/dmgCurve`) — один authoritative-источник для геймплея,
   симуляций и тестов. Это лечит корень drift.
4. **Пометить/починить `balance-math.js`** и прочие симуляции: либо синхронизировать с
   `danger.js`, либо явно подписать «не source of truth, исторический».

### Тест-кейс
- **adapter-contract:** загрузить игру, проверить наличие всех ожидаемых экспортов
  (`P6.hpTime/dmgTime/threatRate`, `G`, `spawn`, `__nxUpdate`, `gfx.floor`, `w2s`, `recalc`,
  `save`) — один smoke-тест, который ловит дрейф ядра до того, как он сломает exploration.

## G8. `maxEnemies` и отсутствие кулла — инвариант (P2)

### Факт
`maxEnemies` (запатчен 300→220) — жёсткий кап; ambient-спавнер уважает его
(`a.enemies.length<i`). Но враги **не despawn'ятся** по дистанции. Дизайн «dormant = данные,
не живые враги» + leash (G3) в основном снимают проблему, но кап можно достичить, если
игрок активирует много encounter'ов и не зачистит их.

### Решение / тест
- Exploration-слой при активации encounter'а проверяет «хватит ли бюджета врагов»; если
  близко к капу — не активировать дальние encounter'ы или применять disengage агрессивнее.
- **Тест-инвариант:** активировать несколько encounter'ов, прогнать sim → `a.enemies.length ≤ maxEnemies`,
  ни один encounter не «завис» в active с невозможностью заспавнить своих врагов (частичная
  активация должна корректно обрабатываться, а не ломать cleared-логику).

## Итог углублённого анализа

Тонкий срез **технически ещё более реалистичен, чем казалось на уровне основного ревью**:
подавляющая часть пивота (отключение директора, spatial difficulty, danger-состав, POI-награды,
маркеры) делается через **уже существующий фасад** `__necro` (P6-функции, мутабельные ссылки,
gfx-хуки, `relics/pacts.push+recalc`). Реально новых патчей ядра нужно **~2** (`spawn`,
`__nxUpdate`-хук). Главные подводные камни — не «переписать движок», а три конкретных
семантических момента: (1) время зашито в **три** разных канала сложности, (2) orchestration
нужен **симуляционный** per-frame хук (не render, не step), (3) leash/disengage и POI-reward —
новая логика, но она cleanly ложится снаружи ядра. Всё это покрывается инвариант-тестами,
которые стоит написать раньше кода.
